## 5. 开工前最值得补齐的五项

### A. 保存 AI 流程当前结论，并补最小交接协议

保存四个核心 AI 环节及程序职责，明确每一环节的输入、输出、证据、失败和恢复。优先定义本轮会用到的结构：材料与来源定位、课程分析草稿、组卷蓝图、成对题答和评分点、检查报告。

需要明确：哪些字段来自原文、哪些是推断或人工修改；各成果绑定哪个材料和课程版本；错误时保留什么、重试什么。先把会跨模块传递的字段和状态约定清楚，不要求提前设计整个系统的全部表。

完成标志：开发者可以按规格构造正常和错误样例，无需自行猜测字段含义。聊天中的旧七阶段提案与最新四环节结论有明确版本关系。

### B. 形成 AGENTS.md 和本轮技术决定

将已确认技术方向、目录和模块职责、统一 API/模型调用入口、字段与版本约定、测试和完成标准写成项目规则。

规则应包含：保持 PRD 的 P0 范围；原型演示值不进入正式规则；任务读取固定输入；网页和两个 PDF 使用同一内容版本；取消后不发布；文件与课程权限不能绕过；修改契约先更新文档和测试。

技术方案中的推荐项应先完成影响本轮的比较或兼容验证，再记录为决定；不要因为文件已保存，就把推荐默认为已批准。也不复制导师项目的框架、固定表数、状态或审核链路。

完成标志：后续 AI 能直接判断本轮允许改什么、固定什么、遇到哪些冲突应报告。

### C. 将 M1 拆成有退出条件的开发轮次

PRD 已有 M0/M1/M2，缺的是更细的执行计划。建议在保留全部 P0 的前提下，按以下顺序组织：

| 轮次建议 | 可检查产出 | 退出条件示例 |
|---|---|---|
| 真实样本与技术验证 | 一门课的代表性材料、可信参考、解析与生成试验记录 | 关键公式/表格可读，出处可定位，模型能产出可检查的题答；失败边界明确 |
| 材料到课程确认 | 真实上传、解析、持久化、课程草稿及确认版本 | 页面与数据库对应；能回到原文件核对；人工修改不被覆盖 |
| 课程到真实练习 | 配置、必要结构确认、题答、检查、网页及两个 PDF | 本轮约定的章节练习从真实入口跑通，题答与文件版本一致 |
| 完善本地闭环 | 完整模拟卷、历史、去重、取消、失败恢复及材料更新 | 达到 M1 对应的全部业务范围和恢复要求 |
| 受邀试用及正式验收 | 账号权限、配额、部署、删除、诊断和正式评测 | 达到 M2 与 PRD 发布条件 |

这是待细化的开发顺序建议，不替代产品需求。首轮验证可以缩小样本和场景，但单章节或单门课跑通不能被记为完整首版完成。用户归属等贯穿性约束应从数据设计开始保留，受邀开放前完成实际隔离验收。

每轮再细化：修改文件、职责和依赖、对应 P0/AC、关键测试、真实数据证据、页面操作路径和稳定提交。无需在第一轮前写完所有未来模块的实现细节。

### D. 将真实样本和 Gold set 从方案变为资产

当前文档知道需要三门课，也定义了 18 个任务、每任务三次的正式评测。当前项目尚未纳入可复现的真实材料及任务清单。

先为一门课准备最小代表性输入：当前范围、对应教学内容、可用试卷与官方解答，并覆盖实际公式、表格或图形。登记文件版本、位置、可信判断和缺口；加入一组可重复的错误输入。

先用于早期技术验证，之后扩展为 PRD 的完整三门课评测集。基线后冻结开放题、难度、重复等阈值，不要求开工前就完成 54 次正式运行。分析与完整生成的 120 秒目标需实际记录，包含必要检查和 PDF。

完成标志：相同输入能重复运行，并可说明输出为什么可信、哪里仍无法判断。

### E. 建立 Git、测试与验收记录

当前目录不是 Git 仓库。正式编码前应建立初始提交、忽略规则和稳定节点；密钥及本地环境不进入提交。工作树是否需要隔离，应按实际并行与变更范围选择。

每轮围绕会影响业务结果的规则先写关键测试，确认测试能暴露缺失实现，再实现并验收。自动化测试优先使用模型替身；真实模型效果验证单独执行并记录成本。

沿用导师三层证据，但对应本产品：

- 状态/功能：自动化检查通过，任务状态和错误处理可运行。
- 内容/数据：真实解析、来源、题答、评分点及数据库记录正确。
- 页面链路：从用户入口完成操作，页面数字、内容及两个 PDF 与保存版本一致。

原型检查可以保留为原型证据；正式产品每轮需有自己的测试、内容和页面证据。

- 正式冒烟、端到端验收、Bug 修复和最终交付尚未到阶段；提前写好相应验收条件即可，不把尚无系统可测视为前期工作全部失效。
