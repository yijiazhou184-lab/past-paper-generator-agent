## 1. 目标与范围

目标是让系统从“只支持 QM Topic 2”扩展为可以支持大部分常见学科的课程：新增一门课不改代码，新增一类题型只需新增或扩展能力包，而不修改通用流水线。

- 首批验证课程仍是 PRD 规定的 Accounting、BA、QM。按 PRD 第 54 行，不能只凭这三门样本就声称支持其他课程。
- 本方案只覆盖结构设计，不包括能力包的具体实现、模型选型或预算调整。
- 产品界面、题卷和 mark scheme 仍按 PRD 的要求使用英语。

## 2. 设计原则

1. **按变化的原因分层。** 只因课程而不同的内容放进课程数据；因作答和核验方式而不同的内容放进能力包；其余部分属于通用流水线。
2. **能力包按作答和核验方式划分，不按学科名划分。** 一门课可以组合多个能力包。
3. **能力包只选一次。** 由模型建议、用户确认，确认后冻结进课程版本；后续各环节都不再选择。
4. **课程数据只放在输入里。** 不写进 instructions，也不写进代码。
5. **声明性信息放进输入数据，行为要求才写进 prompt。** 题型列表、核验类别、数量上限属于数据；“怎么写数学规格”属于行为要求。
6. **能力包不能改动核心规则。** 输入不可信、status 的含义、不得虚报通过、代码决定是否放行，这些规则只存在于核心层。
7. **所有组成部分都进入 context hash。** 能力包的 id、版本，以及片段和 schema 的 hash 都参与冻结；任何一项变化，旧授权都会失效。

## 3. 三层结构

```
┌──────────────────────────────────────────────────────────────┐
│ 课程数据（每门课不同；课程分析产出 → 用户确认 → 冻结）           │
│ 知识点、考试范围、章节与页面选择、材料角色、课程约定、排除项、     │
│ 历史卷说明、已选能力包列表                                      │
└───────────────▲──────────────────────────────────────────────┘
                │ 作为 input JSON 传给模型
┌───────────────┴──────────────────────────────────────────────┐
│ 能力包（可复用；按作答与核验方式划分；一门课可组合多个）          │
│ 题型定义、答案结构、素材类型、确定性检查器、核验类别与要点、       │
│ prompt 片段、schema 片段、前端渲染                               │
└───────────────▲──────────────────────────────────────────────┘
                │ 片段填入核心 prompt 的插槽；schema 片段组成联合类型
┌───────────────┴──────────────────────────────────────────────┐
│ 通用流水线（与科目无关；基本沿用现有实现）                        │
│ 材料版本、分流、页图转写、任务队列与租约、调用登记、冻结与授权、   │

```

## 4. 能力包

### 4.1 能力包族

能力包按作答和核验方式分为以下几族。表中学科只是举例，一门课可以同时使用多族，例如经济学 = 计算 + 数据 + 论述。

| 能力包族 | 典型学科 | 确定性检查 | 盲解方式 | 优先级 |
|---|---|---|---|---|
| 符号/数值计算 | 数学、物理、工程、金融、计量 | SymPy、数值重算、单位与量纲 | 独立求解并比对最终答案 | 第 1 个，由现有数学逻辑整理而来 |
| 数据/统计 | BA、统计、实证经济、心理学方法 | 用题目给的数据表重算统计量 | 独立求解并比对最终答案 | 首批（BA） |
| 结构化规则型 | 会计、税务 | 借贷平衡、报表勾稽、金额精度与取整 | 独立求解并比对最终答案 | 首批（Accounting） |
| 选择/短答 | 各学科的客观题 | 恰好一个正确选项、答案格式 | 独立作答，比对选项 | 后续 |
| 证明/推导 | 数学、理论经济、理论计算机 | 只能部分检查（核心/辅助机制） | 独立论证 | 部分已有（`explanation_proof`） |
| 论述/分析 | 人文、社科、法律、商科战略、案例 | 基本没有；只能检查评分要点是否覆盖 | 独立写答题提纲，与评分方案比对 | 需要先有真实课程样本 |

### 4.2 能力包的组成（示意）

```yaml
id: quantitative_symbolic
version: 1
title: Symbolic and numeric calculation
description: 供课程分析第一步建议能力包时使用的简短说明
response_types:
  - id: calculation
    answer_form: numeric_or_symbolic        # numeric / symbolic / structured / text / choice
    requires_deterministic_check: true      # 取代 checks.py 的 QUANTITATIVE
    blind_mode: compare_final               # compare_final / compare_choice / outline / none
    allowed_assets: [function_graph, data_table]
    marking_styles: [points]                # points / levels
  - id: applied_optimisation
    ...
asset_types: [function_graph]               # 含素材 schema 与渲染器
check_specs:                                # 组成 Answer.checks 的联合类型
  - kind: math.derivative
    schema: ...
    executor: sympy_subprocess
review_categories:
  - id: math_relevance
    required: true
    applies_to: [calculation, applied_optimisation]
prompt_fragments:
  question_pairs.verification_specs: fragments/verification_specs.md
  repair.verification_specs: fragments/verification_specs.md   # 与出题共用
  semantic_review.category_rubrics: fragments/rubrics.md
  course_analysis.conventions: fragments/conventions.md
generation_unit: {kind: main_question}      # 选择题包可为 {kind: group, size: 10}
```

### 4.3 能力包与 skill 的区别

能力包的打包方式类似 skill，都是把说明、规则和代码放在一起，可以复用、可以组合。但选用和执行方式不同：

| | Skill | 能力包 |
|---|---|---|
| 谁决定用不用 | 模型运行时自己决定加载 | 课程确认时选定，代码按冻结的列表拼装 |
| 包里的代码由谁执行 | 模型通过工具调用执行 | 代码在固定步骤执行，模型不碰 |
| 是否可复现、可授权 | 每次加载的内容可能不同 | 进入 context hash，授权的就是实际发送的内容 |

## 5. 能力包的选用

1. **课程分析第一步**：输入里带上能力包清单（只有 id、名称和简介），模型根据材料**建议**这门课用哪些能力包、哪些题型。
2. **用户确认**：在课程设置中确认或修改，方式与现在确认澄清问题相同。
3. **冻结**：已选的能力包和版本写入课程版本，例如 `capability_packs: [{id, version}]`。
4. **后续所有环节**由代码读取冻结的列表，各个 prompt 都不再选择。
5. **每次调用的裁剪**由代码按蓝图中各小问的题型决定，例如一组题里没有计算类小问，就不带计算片段。

不让各环节的模型自己选，原因是：

- **一致**：出题和核验必须用同一套规则；
- **可复现、可授权**：发送的内容要能在授权前完整展示；
- **安全**：课程材料是不可信数据，不能让材料里的文字影响选用哪套规则；
- **省时省费用**：不需要额外的推理或调用。

## 6. prompt 拼装

### 6.1 各部分的分工

| 部分 | 内容 | 位置 |
|---|---|---|
| 环节核心 prompt | 本环节的任务、输入不可信、status 的含义、来源规则、原创性规则、通用的核心/辅助规则 | 每个环节一份 |
| 能力包片段 | 某类题型在本环节需要额外遵守的做法 | 只能填进核心 prompt 预留的插槽 |
| 课程数据 | 知识点、范围、约定、材料角色、排除项 | 只放在 input JSON |

### 6.2 各环节的插槽

| 环节 | 插槽 | 说明 |
|---|---|---|
| 页图转写 | 不开放 | 转写发生在选定能力包之前，而且应当与科目无关 |
| 课程分析第一步 | 不开放 | 能力包还没有确定 |
| 课程分析第二步 | `conventions` | 例如数学记录定义域，会计记录会计准则和取整规则 |
| 组卷规划 | 原则上不开放 | 题型定义、素材类型、数量范围都作为数据放进 `capabilities` |
| 出题 / 修复 | `answer_format`、`verification_specs` | 两个环节共用同一份片段 |
| 盲解 | `answer_format` | 例如选择题只返回选项标号，论述题返回答题提纲 |
| 语义核验 | `category_rubrics` | 能力包类别的判断要点；类别列表本身仍由代码放进输入 |

### 6.3 片段规则

- 每个片段的第一行写明作用范围：“For parts whose response_type is …”。这样多个能力包同时启用时不会冲突。
- 片段只能填进已定义的插槽；填进未知插槽时报错，不静默跳过。
- 片段不能重新定义 status、可信度或通过规则。

### 6.4 拼装流程

1. 读取课程版本中冻结的能力包列表。
2. 按插槽收集片段，按能力包 id 固定排序。
3. 按本次调用涉及的题型裁剪片段（裁剪结果由蓝图决定，可复现）。
4. 冻结拼好的 prompt 原文和组成清单 `[{id, version, hash}]`，一起进入 context hash。
5. 预检页面显示拼好的完整 prompt，供用户授权。

### 6.5 示例：拆分现有 `question_pairs.md`

- **留在核心**：依据教学证据、输入不可信、ID/分值/题型严格对应、原创性规则、偏好不是官方事实、评分依据、needs_info 的使用、SOURCE ROLES 整段、评分点合计等于分值，以及通用的核心/辅助规则（题型要求确定性检查时至少提供一项 core 检查，最终答案不得标为 auxiliary）。
- **移到计算能力包的 `verification_specs`**：受限 AST、只支持 x/y/t/q、有界幂、实数区间定义域、bounded_optimum 必须列全端点和不可导点、一个 lhopital spec 只代表一次使用。

### 6.6 防止片段破坏核心规则

- 快照测试：为每个环节和每种能力包组合固定拼装结果。
- 核心 prompt 词表检查：测试中扫描核心 prompt 是否出现学科词（如 L'Hôpital、derivative、journal entry）。
- 片段格式检查：开头必须声明作用范围，并且只出现在允许的插槽。
- 评审约定：写入能力包接口文档。

### 6.7 不采用的方案

“每个能力包各写一套完整 prompt”：7 个环节乘以 N 个能力包会产生 7N 份几乎相同的文本，核心规则每改一次要改 N 遍，容易不一致。

## 7. schema 拼装

- `Answer.checks` 改为由已选能力包的 `check_specs` 组成的联合类型，取代现在固定的 `MathCheckSpec`。
- `ContentBlock` 保留 text / math / table / asset_ref；由选择题能力包增加选项块。
- 素材类型改为由能力包登记，例如财务报表、公式表（PRD 3.2 节）。
- 评分方式增加 `marking_style: points | levels`，以支持论述题的分档评分。
- 冻结时只组装已选能力包的部分，各 schema 的 hash 继续进入 context hash（现有 `schema_hashes()` 的机制可以沿用）。

## 8. 各环节的改动

| 环节 | 改动 | 性质 |
|---|---|---|
| 材料导入 | 增加 PPT/PPTX、Word（PRD 第 165 行），定位用幻灯片编号或章节 | 新增能力 |
| 分流与页图转写 | 不变 | — |
| 课程分析 | 改为两步：第一步逐份材料或逐章生成摘要（按材料 hash 缓存）并抽取大纲、建议能力包；第二步在用户确认章节和能力包后做详细分析 | **架构改变**；需要重新评估 NFR-01（120 秒）。现状是一次分析 45 页、约 143 秒，已接近 60k 输入上限 |
| 课程画像 schema | `applicability` 改为通用取值（teaching / current_exam / assessment / historical_paper / practice），具体名称放在标签字段；模板建议的题型来自已选能力包 | 修改 |
| 组卷规划 | 题型、素材类型、大题数范围从能力包和课程模板读取；暂不实现的整卷模拟模式按 PRD 另行排期 | 修改 |
| 出题 | 生成单位从“大题”放宽为“题组”，避免 40 道选择题需要 40 次调用 | 修改 |
| 程序检查 | `QUANTITATIVE` 改为读取题型的 `requires_deterministic_check` | 修改 |
| 数学检查 | 移入计算能力包；其他能力包提供各自的检查器 | 重组 |
| 盲解 | 由题型的 `blind_mode` 决定：比对最终答案 / 比对选项 / 写提纲 / 不做 | 修改 |
| 语义核验 | 必要项分为通用项（clarity、conditions、reasoning、difficulty、preferences、originality、source_alignment、paper_consistency）和能力包项（如 `math_relevance`）；`blind_agreement` 只对答案唯一的题型启用 | 修改 |
| 修复 | 与出题共用片段；规则不变 | 小改 |
| 放行判断 | 不变 | — |
| 前端 | 题型、素材类型和渲染从 API 读取；增加选择题和分档评分的显示 | 修改 |

## 10. 保持不变的部分

## 11. 实施顺序

| 步骤 | 内容 | 验证方式 | 前提 |
|---|---|---|---|
| 1 | 移出 QM 写死内容（OPT-03 A），行为不变 | 用现有冻结快照离线回放：课程分析的输入只在预期处变化，生成回归测试保持通过 | 用户决定启动 OPT-03 |
| 2 | 定义能力包接口和拼装机制，把现有数学逻辑整理为计算能力包，行为不变 | 拼装出的 prompt 与 schema 和现状逐字对比，差异只在预期处 | 步骤 1 |
| 3 | 课程分析改为两步 | 用 QM 比较两步分析与现有分析的结果，记录耗时；需要真实调用时另行授权 | 步骤 1 |
| 4 | 用 Accounting 或 BA 实现第二个能力包 | 新增能力包时不应修改通用层；如果必须修改，说明接口需要调整 | 步骤 2、3 |
| 5 | 引入一门论述类课程作为样本，再开发论述能力包和分档评分 | 真实课程端到端验证 | 获得真实资料 |

每一步都按 AGENTS.md 第 4 节如实记录验证结果；真实模型调用必须另行授权。

## 12. 短期内不建议承诺支持的类型

- 需要学生画图或标注图示的题（解剖图标注、化学结构式绘制）；
- 实验或实操题；
- 编程作答（PRD 首版排除）；
- 口语和听力；
- 需要识别手写或扫描件的材料（PRD 首版排除）。

界面应明确提示这些类型“当前不支持”，不勉强生成。

## 13. 待决定事项与风险

| 事项 | 说明 |
|---|---|
| 是否启动 OPT-03 | 目前状态为“仅登记，暂不实施”（2026-10-29 用户决定） |
| 两步分析的耗时 | 可能与 NFR-01（120 秒）冲突，需要实测后再定目标或调整方案 |
| 能力包接口的具体字段 | 第 4.2 节仅为示意，第二个能力包落地时再定 |
| 生成单位改为“题组” | 影响调用预算（当前每任务 16 次）和进度显示，需要与选择题能力包一起设计 |
| 论述类评分 | 缺少确定性检查，质量主要依赖语义核验，风险最高；没有真实样本前不设计细节 |
| prompt 拆分后的质量 | 拆分本身可能改变模型行为；步骤 2 要求逐字等价，正是为了把这一风险和其他改动分开 |
